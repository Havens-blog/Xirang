# Freeform Expert Review

评审对象：`docs/proposals/platform-console/proposal.md`（平台控制台子项目：统一入口 + 身份治理 + 权限管理 + 工作台）
评审视角：企业门户与身份治理前端架构师（平台控制台 · SSO · 零后端纯前端）

## Background Assessment

本提案要解的问题我非常熟悉：ecmdb-web 下线后，平台级登录页、身份治理/权限管理 UI 与统一入口失去宿主，而 e-cam-web 是云管业务前端，不应被塞进平台治理职责。提案的解法是新建一个独立的纯前端控制台子项目，直调 eiam 既有 HTTP API，复用 eiam 写入的共享 Redis session，与 e-cam-web 单点互通；同时把 e-cam-web 里孤立的 `platform/users` 页面迁出，完成边界清理。方案的两个关键取舍——拒绝 BFF/聚合层/微前门外壳、工作台收敛为纯 eiam 侧（欢迎 + 我的信息 + 快捷导航）——正是企业「门户与业务应用分家」时最容易被做歪的两处，提案把它们钉进了 Out of Scope。

通读全文，这个方案成立依赖三个前提假设。其一，共享 session 与 e-cam-service 认证中间件的兼容是「天然」的，后端因此零改动。其二，eiam 的 API 面足以覆盖原 ecmdb-web iam 管理页的全部操作，以 Phase 0 端点差集盘点兜底。其三，控制台能与 e-cam-web 处在同一登录域下，cookie 得以共享，SSO 得以成立。这三个假设恰好是这类项目历史上静默失败最集中的位置：第一条是断言而非核验结论，第二条被推迟到开工后的盘点，第三条在部署形态上存在未调和的矛盾。我的评审就围绕这三条展开。

## Key Risks

最大的问题出在部署形态与 cookie 口径上，提案全文没有把这两条约束放在一起核对过。

风险：CDN 静态托管与「同一登录域」的 cookie 共享前提存在未调和的冲突，跨域直调还牵出 CORS 与 SameSite 两道墙。
> "纯静态前端站，可 CDN 托管，首屏资源可缓存。" 与 "控制台需与 e-cam-web 在同一登录域下" —— 若控制台静态站最终落在与 eiam/e-cam-web 不同的源上，纯前端直调 eiam 的请求就是跨站请求：共享 session cookie 会被浏览器 SameSite 默认策略拦下，eiam 若未配置 CORS 则请求根本发不出去，而给 eiam 补 CORS 恰恰是后端改动，直接击穿「除 eiam 外不新增后端、零改动」的承诺。这两条 NFR 单独看都对，放在一起提案没有给结论，实现者会按各自理解选边，选错的那条要到联调期才暴露。

风险：「天然兼容、后端零改动」是一个未经源码核验的断言，被当成了前提而非待验证项。
> "登录态复用 eiam 写入的共享 Redis session——与 e-cam-service 认证中间件（`EcmdbAuthMiddleware` 已在读该 session）天然兼容，后端零改动。" —— 这类对接我反复吃过亏：认证中间件除了读 session 之外，往往还读 cookie 名与属性、租户来源、CSRF token，或校验 Origin/Referer。只要 EcmdbAuthMiddleware 的读取口径里有任何一项与新登录页的写入口径不一致，SSO 就是静默失败——用户看似登录成功，跳到 e-cam-web 却 401，且日志里没有任何指向根因的报错。提案的风险表自己也承认这一点（"登录态/SSO 对接不准（cookie/session 格式不兼容）"），但缓解措施只有 "照抄 ecmdb-web 现状的登录/session 写入口径"，通篇没有一个动作去核对 EcmdbAuthMiddleware 到底读什么。没有读取口径清单，「照抄」无从谈起。

风险：单点登出（Single Logout）语义完全缺席，成功标准只覆盖了「登入互通」这一半。
> "用户从控制台工作台/顶部导航单点跳转入 e-cam-web，共享会话、不重复登录。" —— 共享会话意味着双向责任：在控制台登出后，已打开的 e-cam-web 标签页必须随下一次请求失效并跳登录页；反过来从 e-cam-web 登出也必须使控制台会话失效。跨应用登出正是 cookie domain/路径口径不一致最先爆雷的位置——删错域或路径，session 实际未销毁，登出变成假动作。而成功标准里只有 "控制台可完成密码登录与登出"，单应用、单方向，测不出这类问题。

风险：验证硬性标准本身立得住，但验证环境的宿主口径没有定义——这最容易让「真实浏览器验证」假通过。
> "登录/登出、SSO 跳转、身份治理/权限管理核心链路必须经**真实浏览器**验证（Playwright 或浏览器 MCP 自动化），不接受仅单测/接口级验证" —— 这个立场我完全赞同，这也是本提案写得最硬的一条。但 SSO 跳转验证的前提，是控制台与 e-cam-web 跑在会共享 cookie 的同域路径下。本项目已有前例证明过这类坑：e-cam-web 必须经 `8888/cam` 的 nginx 反代联调，dev server 直连会因缺 `/api/iam` 代理而认证必挂。若控制台在开发/验证环境的宿主（端口、路径、反代配置）不在提案里钉死，验证结果要么假失败，要么更糟——在两个互不相干的端口上各自「验证通过」，部署到同域环境后口径全变。

风险：Phase 0 盘点只有「列缺口」，没有「缺口怎么办」的决策路径，而唯一的补法（扩 eiam 端点）与零后端约束相抵。
> "错误情况：eiam 某端点缺（部分身份/权限操作无对应 API）→ Phase 0 盘点兜底，UI 降级提示。" 与 "依赖 eiam 已有 HTTP API（`/api/iam/user/*` 等）与 session 机制，eiam 必须保留且稳定。" —— 「UI 降级提示」只能兜住查看类缺口，兜不住操作类缺口：如果缺的是角色-策略绑定、LDAP 身份源配置这类写端点，降级提示等于功能没有；而补端点意味着改 eiam。Out of Scope 只排除了 "eiam 本身替换（保留 eiam，含其 SDK/服务）"，没有说清「扩展 eiam 端点」是否被允许、由谁承接。盘点做完然后呢？提案没有回答，而这恰恰决定项目是减配交付还是中途返工。

风险：platform/users 迁出没有设「能力对齐」顺序门，存在先把旧 UI 拆了、新 UI 又覆盖不了的反向断供窗口。
> "从 e-cam-web 迁出平台身份 UI（`platform/users`），消除双处维护。" 与缓解措施 "先盘点引用关系，灰度迁移，保留回退" —— 盘点引用、保留回退都对，但顺序没定：迁出应当以「控制台对 Phase 0 清单逐项覆盖完成」为前置门。否则一旦 eiam 端点缺口导致控制台缺某个操作，而 e-cam-web 里那一页又已迁走，平台身份管理就会出现比现状更糟的真空——提案要防的 "断供" 以另一种形式发生。

问题：「可行，无 showstopper」的结论建立在提案自己承认的唯一未验证项之上，属于循环论证。
> "可行，无 showstopper：eiam API 已存在并在生产运行；session 机制已与 e-cam-service 认证中间件解耦（共享 Redis）。唯一需验证的是 eiam API 面对身份治理/权限管理的覆盖度（Phase 0 盘点）。" —— API 存在与覆盖足够是两回事。eiam 在生产运行只证明登录/鉴权链路可用，不证明原 iam 管理页的每个增删改查都有对应端点。在 Phase 0 跑完之前给出「无 showstopper」的定论，等于用尚未执行的验证去佐证自己。

问题：v1 范围包含全部四种登录流程，但成功标准只硬性要求密码登录，且 LDAP/passkey/MFA 的真实浏览器验证可操作性没有交代。
> 范围项 "登录/登出（eiam system/LDAP/passkey/MFA 流程）" 对成功标准 "控制台可完成密码登录与登出；LDAP/passkey/MFA 沿用 eiam 能力并补 UI 入口" —— 两条口径不一致，执行者只能自行揣测做到什么程度算完。更麻烦的是验证标准写了「必须经真实浏览器验证」，而 LDAP 需要 LDAP 服务器、passkey 需要认证器、MFA 需要设备，这三类流程的浏览器闭环怎么做、能否以 eiam 现网行为为基准降级为冒烟，提案只字未提——硬性标准落在这三条流程上会变成无法执行的空文。

问题：ecmdb-web 同时承载的 ticket/change 被排除出范围，但没有交代归宿，「断供」会换一种形式发生。
> "工单（ticket）/ 变更（change）" —— 提案动机写明 "一旦下线 ecmdb-web，平台身份/权限管理 UI 直接断供"；按同样的逻辑，ecmdb-web 下线后 ticket/change UI 同样断供。Out of Scope 把它们排除了，却没有声明这是「有意的退役」还是「挂起待后续提案」。若是遗漏，去 ecmdb-web 的目标完成之日就是工单/变更功能无声消失之时。

问题：tenant_id 租户选择语义只剩一句括号，登录页如何选租户、SSO 跳转如何携带租户上下文都没有定义。
> "控制台需与 e-cam-web 在同一登录域下，共享认证/租户选择语义（eiam 以 tenant_id 区分租户）。" —— 租户选择是我踩过最久的坑之一：登录页上租户是下拉选择还是自动推断、选完后 tenant_id 存在 session 还是 cookie、跳转到 e-cam-web 后它从哪里取得同一份租户上下文——任何一处口径不对，用户会「登录成功但看到错租户的数据」，这类错误比 401 更隐蔽、更难排查。一句话括号不足以指导实现。

问题：「会话过期统一跳回登录页」隐含了对 e-cam-web 现有 401 处理的改造，这项改造没有出现在任何范围清单里。
> "边界情况：会话过期 → 统一跳回登录页；无权限操作 → 明确提示而非白屏。" —— 今天 e-cam-web 会话过期后跳的登录页大概率就是 ecmdb-web 的 login 视图；ecmdb-web 下线后，这个跳转目标必须切到新控制台。In Scope 只列了 "从 e-cam-web 迁出平台身份 UI（`platform/users`），消除重复"，没列「切换 e-cam-web 的过期/401 跳转目标」。这是一处必然发生的 e-cam-web 前端改动，游离在范围之外意味着没人认领，到时候「统一跳回登录页」统一不了。

## Improvement Suggestions

以下建议按影响排序，前四条建议在进入 PRD 之前落掉。

建议：把部署形态钉死为「同一登录域下的反代路径」，CDN 仅作静态资源加速层，并补一份 CORS/SameSite 需求核对说明。
Addresses: CDN 托管与同一登录域冲突的风险，以及验证环境宿主口径未定义的风险。
> What changes: 在 Constraints 中明确控制台在开发与生产环境的宿主口径——例如与 e-cam-web 同域、经 nginx 反代挂独立路径（沿用 `8888/cam` 的既有前例），并声明「跨域 CDN 域名直调 eiam」不被支持；若坚持 CDN，则必须先核实 eiam 的 CORS 配置与 cookie SameSite 属性，把任何「需要改 eiam」的点显式列单。验证一节相应补一句：SSO 闭环必须在最终同域宿主形态下执行，不得在各自独立端口的 dev server 上判定通过。采纳后，cookie 共享从口头约束变成有明确宿主拓扑支撑的工程事实。

建议：增加一个「认证链路事实核查」前置任务，产出 cookie/session 读写兼容矩阵。
Addresses: 「天然兼容、后端零改动」未经核验的风险。
> What changes: 在 Phase 0 之前或并列，安排读两份源码：EcmdbAuthMiddleware 实际读取的凭证载体（cookie 名、属性、是否校验 Origin/Referer/CSRF、租户来源）与 eiam 登录端点实际写入的口径（同名同域同路径、session 结构、tenant_id 存放位置），逐项对表产出兼容矩阵。矩阵中任何一项对不上，都回写为显式任务，而不是靠「天然」二字过关。这也是「照抄 ecmdb-web 现状写入口径」唯一能落地的方式——先有口径清单，才谈得上照抄。租户语义的结论也应从这里来，顺带解决 tenant_id 只剩一句括号的问题。

建议：把单点登出补进成功标准，并纳入真实浏览器闭环。
Addresses: Single Logout 缺席的风险。
> What changes: 成功标准追加两条：控制台登出后，已打开的 e-cam-web 会话在下一次请求时失效并跳转控制台登录页；从 e-cam-web 登出后反向同理。验证方式与 SSO 跳转共用一条真实浏览器链路（双标签页操作），因为跨应用登出只能在同域双应用环境里测出来。

建议：Phase 0 产出升级为「带决策门的缺口处置报告」。
Addresses: 缺口无兜底路径的风险，以及「无 showstopper」循环论证的问题。
> What changes: 每个盘点出的缺口必须标注三类处置之一：UI 降级提示可接受（限查看类）、需扩展 eiam 端点（显式声明为对 eiam 的改动，另立任务或提案）、放弃该能力（需业务确认）。并给出一个可判断的启动门槛（例如操作类写端点缺口数为零才进入开发），替代现在 "Phase 0 需盘点「原 ecmdb-web iam 页面的后端端点清单」与「eiam 现有端点」的差集，作为任务拆解输入。" 的单向表述。这样 "能力不低于原 ecmdb-web 的 iam 管理页（按 Phase 0 盘点清单逐项覆盖）" 才从一句口号变成可逐项核验的验收依据。

建议：为 platform/users 迁出设置能力对齐顺序门，迁出动作绑定回归清单。
Addresses: 迁出顺序门缺失的风险。
> What changes: 在任务拆解中把「迁出 platform/users」显式排在「控制台对 Phase 0 清单逐项覆盖完成」之后；迁出 PR 附带三样东西：引用盘点结果（路由/菜单/跳转入口，含 e-cam-web 内部对 "孤立页面" 的隐性链接排查）、e-cam-web 云管核心链路的真实浏览器回归清单（把成功标准里的 "e-cam-web 迁出平台身份 UI 后云管功能无回退（走查通过）" 明确为浏览器自动化走查而非口头走查）、以及回退方案（保留可恢复的分支或 tag）。

建议：明确 ticket/change 的处置决定，并在 Problem 一节同步声明。
Addresses: ticket/change 归宿未交代的问题。
> What changes: 二选一写清楚：要么在 Out of Scope 中把该项改写为「有意退役，平台不再提供 ticket/change UI」，要么标注「挂起，ecmdb-web 下线前另立提案承接」。无论哪种，都要让读者知道去 ecmdb-web 之后这批能力的去向，而不是靠 Out of Scope 的沉默。

建议：补一节租户选择语义说明。
Addresses: tenant_id 语义只剩一句括号的问题。
> What changes: 明确登录页的租户选择交互（下拉/自动推断）、tenant_id 在共享 session 中的存放位置、SSO 跳转后 e-cam-web 从何处取得同一份租户上下文、以及切换租户时的行为（重新登录还是热切换）。这些结论应来自认证链路事实核查（上一条建议），而不是新设计——租户口径上，照抄现状永远优于自创。

建议：澄清四种登录流程的范围与验证口径。
Addresses: 范围与成功标准口径不一致、硬性验证在 LDAP/passkey/MFA 上不可操作的问题。
> What changes: 二选一：要么把 v1 范围收敛为密码登录，LDAP/passkey/MFA 移入后续迭代（更符合 YAGNI，且不影响 "沿用 eiam 能力" 的底线）；要么保留四流程但写明验证口径——密码登录走完整真实浏览器闭环，LDAP/passkey/MFA 各至少一条真实浏览器冒烟，外部设施不可得时明确记录依赖并以 eiam 现网行为为基准。避免范围写四个、标准只硬性要求一个、验证细则一个都没有的三层落差。

建议：把「e-cam-web 401/过期跳转目标切换到控制台登录页」列为 In Scope 的显式任务。
Addresses: 会话过期统一跳转归属缺失的问题。
> What changes: 在 In Scope 与成功标准各加一条：e-cam-web 的会话过期/无权限跳转目标更新为控制台登录页，纳入 e-cam-web 回归走查清单。同时注意这也是部署形态建议的前置依赖——跳转目标写相对路径还是绝对 URL，取决于最终同域宿主形态，两件事应在 PRD 里互相引用。

建议：把「视觉对齐」具体化为共享 UI 组件库版本与主题 token，而不是手工抄样式。
Addresses: 提案自列的 "新前端与 e-cam-web 视觉/组件不统一" 风险，以及 "v1 先视觉对齐；共享设计资产另立提案" 隐含的样式漂移隐患。
> What changes: 在 Constraints 里把 "控制台与 e-cam-web 需共享视觉体系与交互一致性，避免两套产品体验" 落到可执行的两件事：控制台与 e-cam-web 使用同一 UI 组件库的同一版本；主题 token（色彩/间距/字号变量）以文件形式共享而非复制粘贴。这样即便设计系统沉淀另立提案，v1 也不会长出第二套观感。
