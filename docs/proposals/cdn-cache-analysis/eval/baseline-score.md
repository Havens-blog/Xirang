## Phase 1 — 推理审计(独立于 rubric)

### 1.1 论证链追踪

**问题 → 方案**: 问题定义(CDN 缓存健康度四问:命中率/未命中定位/回源浪费/优化建议)与方案(CDN Tab 内嵌缓存分析卡,双命中率 + 域名/URI/状态码 + 结构化优化项)匹配,无"解了另一个更简单的问题"之嫌。基本成立。

**方案 → 证据**: 证据真实(实测 1453 万请求/1h、datasink.jlc.com 286 万、cache_hit/sum_bytes 可聚合),但存在两个脱节:
- 证据只给了**请求规模**,从未给出当前实际命中率 / 未命中占比 / 回源浪费的**基线数字** — 一个"命中率分析"提案没有自己的命中率基线数据,"浪费"是推断而非测量。
- "可量化到金额级"是**断言**而非量化(全文无任何金额示例)。

**证据 → 成功判据**: SC 大部分可测,但**核心价值(优化项)只测"存在性 ≥3",不测正确性/可执行性/效果**,以及档位阈值、前窗"下降>阈值"提示的阈值从未定义。

**自相矛盾检查(SC 一致性深潜)**: 见 1.2。

### 1.2 SC ↔ InScope 一致性深潜(全对扫描 + 区域聚类)

受影响区域聚类:
- **后端聚合/接口簇**: SC-1, SC-2, SC-3, SC-4(回归), InScope-1, InScope-2, InScope-4, InScope-5
- **前端卡簇**: SC-1(入口), SC-2(展示), SC-4(不白屏), InScope-3
- **规则引擎簇**: SC-5, InScope-2

全对双向推导结果:

```
CONTRADICTION: SC-1 "手动触发后 ≤ 2 次聚合查询返回分析结果" ↔ InScope-1 "当前窗并发聚合 cache_hit×host(域名)、×uri(URI 未命中)、×status(状态码命中率)+ sum_bytes(字节命中率)+ 前窗 1 帧(cache_hit 分布对比)"
| Type: resource-contention / direction-clash(语焉不明,需作者澄清)
| Evidence: SC-1 与 NFR"一次分析 ≤ 2 次聚合查询(当前窗 + 前窗)"要求全分析 ≤2 次聚合;InScope-1 描述当前窗为 4 路并发聚合(host/uri/status/sum_bytes)+ 前窗 1 帧。若 4 路并发为 4 次独立 /aggregate 查询,则总量 ≥4(甚至 5),与 ≤2 冲突;仅当"并发聚合"被坍缩为单次多分组扫描时才可能同时成立。方向一(满足 InScope-1 → 违反 SC-1)成立。
| Resolution required: 声明"2 帧 = 2 个时间窗(当前+前窗),每帧可含 N 路并发聚合"或把 SC-1/InScope-1 改写为一致的计数口径
```

```
AMBIGUOUS: SC-4 "前窗对比给出命中率变化(↑↓)" ↔ Requirements 场景 "前窗无数据 → 只给当前窗绝对量判定"
| Type: direction-clash
| Evidence: 场景已定义前窗无数据的降级行为,但 SC-4 未附带该豁免;按字面,前窗为空时 SC-4 无法满足。
| Resolution required: 在 SC-4 中显式写入"前窗无数据时豁免 ↑↓ 输出"的例外
```

```
AMBIGUOUS: SC-2 "状态码命中率" ↔ InScope-2 "4xx/5xx 占比 → 结构化优化项 ≥3"
| Type: 指标语义漂移
| Evidence: SC-2 列的是"状态码命中率"(按状态码的缓存命中率),InScope-2 与场景"状态码命中率低(4xx/5xx 占比高)"混用"状态码命中率"与"4xx/5xx 占比"两种口径,未定义"命中某 4xx 响应"到底算不算命中。
| Resolution required: 统一为单一指标(如"各状态码的命中率 + 4xx/5xx 流量占比")并定义错误响应的 hit 语义
```

结论: 1 处确认的资源冲突/含糊 + 2 处语焉不明。SC 内部一致性存疑。

### 1.3 Pre-score Anchors(将汇入 blindspot 或对应维度)

- A. 查询预算矛盾:SC-1/NFR"≤2 次聚合查询" vs InScope-1"4 路并发 + 前窗 1 帧"。
- B. 无命中率/浪费基线数字,"可量化到金额级"未量化。
- C. SC 只测优化项"存在",不测正确性/效果。
- D. "复用 WAF 诊断骨架 / 复用 llm 包 / 团队已完整实现"为无出处的断言(未陈述假设当事实)。
- E. "未命中流量占比"未定义按请求还是按字节计(成本相关性取决于字节口径)。
- F. SC-3 只测"同一窗口可复现"(同源自洽),未测跨源口径一致性,与风险表"补跨源口径测试"脱节。

## Phase 3 — Blindspot 猎取(均带原文 quote)

1. **[blindspot] 优化项正确性闭环缺失**: SC 只测"结构化优化项 ≥3",从不验证建议正确性/采纳后是否真正降低回源 — 功能诊断了问题,成功判据却只数建议条数,不数效果。原文: "结构化优化项 ≥3(含域名/URI 前缀 + 建议动作 + 未命中流量占比)" — 需在 SC 加入建议有效性验证(如抽样人工复核或采纳前后命中率对照)。

2. **[blindspot] 与云侧报表口径不一致的审计信任风险**: 风险表自己承认 "partial/error 归入口径与云侧报表不一致引发质疑",缓解是"文档化" — 文档化已知不一致不会让读者信任数字,用户拿结果与阿里云控制台对比必然对不上。原文: "命中=hit+partial、未命中=miss+error 文档化;口径以 cache_hit 分布可复现为准" — 需补与云侧口径的对齐策略或差异说明。

3. **[blindspot] "用户确认"陈述无证据**: Assumptions Challenged 表中"用户确认内嵌""用户确认双口径""用户确认结构化""用户确认手动触发+前窗对比" — 四个"用户确认"以事实口吻给出,无任何访谈/评审记录,是不可复核的断言(CTO 模式:未陈述假设当事实)。

4. **[blindspot] 状态码命中率语义未定义**: "状态码命中率低(4xx/5xx 占比高)→ 缓存对错误响应无效,建议回源校验/缓存规则排除错误码" — 缓存对错误响应的 hit/miss 语义(命中一个被缓存的 404 算不算 hit?)在方案/Scope 中无定义,规则引擎据此输出建议时口径悬空。

5. **[blindspot] 核心价值"可量化到金额级"全文未量化**: 唯一的价值锚点是回源费用,但提案自始至终无一个金额/命中率基线数字,优化优先级排序("未命中流量占比")也无按字节计的明确定义。原文: "请求命中率与字节命中率的差距直接对应回源带宽 / 流量费用浪费...可量化到金额级"。
