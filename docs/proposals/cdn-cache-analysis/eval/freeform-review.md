# Freeform Expert Review

## Background Assessment

我是在自建统一日志查询平台(联邦聚合 /aggregate)之上做了十年多云 CDN 健康度与回源优化的人,见过太多"命中率数字好看但回源账单难看"和"某个源口径没归一导致月报命中率虚高"的事故。这份提案想解决的问题我完全认同:运维需要一个能快速回答"缓存健康度怎么样、哪些域名/URI 失效最重、回源浪费多少、该怎么优化"的结论性输出,而现有日志查询只有原始聚合(Total/TopN/趋势),靠人工逐域名逐 URI 排查不可规模化。

在我读来,方案的核心技术路线是:在日志查询 CDN Tab 内嵌"缓存分析"卡(手动触发,镜像 WAF 流量诊断卡交互),后端对当前窗口 + 前一等长窗口做聚合,规则引擎输出双口径命中率(请求 + 字节)、域名命中率排行、未命中 URI TOP、状态码命中率与结构化优化项(域名/URI 前缀 + 建议动作 + 未命中流量占比),AI 解读后置且失败降级。它之所以敢承诺"做出来即日可用"且"同构复用估 1-1.5 天",依赖三个前提:数据面零新增采集(统一模型已含 cache_hit 与 bytes_sent,聚合白名单已实测覆盖);跨源 cache_hit 归一映射已有,只需补测试;WAF 诊断骨架(聚合并发、前窗对比、SWR 缓存、per-source 降级、AI 后置)可以整套复用。

我对意图的读法与提案自身有一处分歧,先摆出来:提案把"请求命中率与字节命中率的差距"几乎只归因于"大文件未命中 = 回源带宽浪费",但以我的经验,这个 gap 还有另一面——小文件大量 miss 会让请求命中率塌陷而字节命中率尚可,对应的是回源请求数/QPS 与按请求计费的浪费,是另一类优化目标。这个分歧会贯穿后面多条评审。另外,我去代码里核对了提案反复引用的几处"既有事实",其中至少两处(EdgeOne 的 cache_hit 映射、WAF 诊断骨架的 WAF-only 硬门槛与真实查询数)与当前实现不一致,这影响的是可行性本身,不只是措辞。

## Key Risks

我按"先口径、再归因、再成本、最后可靠性"的顺序说,这也是我评审命中率方案的习惯:分子分母不锁死,后面所有数字都没有意义。

**先说双口径的分子分母。** 字节命中率是本次提案最实的抓手,也是我最不放心的一处。

风险：字节命中率把 partial 全量计入命中,会系统性高估字节命中率、低估回源浪费,与"量化到金额级"的目标相悖
> "字节命中率(hit+partial 字节/总字节)" —— partial 在日志里通常是"部分命中"(Range/分片/缓存刷新部分命中),其 bytes_sent 是缓存与回源字节的混合,日志并不区分;把 partial 全部算作命中字节,大文件分片场景下字节命中率会被明显抬高,"请求-字节 gap"被人为缩小,回源浪费被低估。更麻烦的是 partial 的跨源语义差异很大:当前代码 NormalizeCacheHit(D:\Haven\e-cam-service\internal\shared\cloudx\logquery\types.go)把 Akamai 的 "TCP_REFRESH_HIT"(含 MISS)归为 miss、把 "TCP_REFRESH" 归为 partial,而 DCDN 的 hit_info partial 与离线 HitInfo 的 partial 又是另一套值——不同源的 partial 对"命中"的贡献根本不是同一把尺子,提案的公式却把它们都当 100% 命中求和。

问题：请求命中率的分母是"总请求",混入了天然不可缓存的请求,健康档位会被工作负载稀释
> "请求命中率(hit+partial/总请求)" —— 动态接口、POST、带认证的请求、4xx/5xx、Range 请求等天然不可缓存,统统躺在分母里。同一个缓存规则水平,纯静态站点命中率可以 95%+,重动态域名可能永远到不了 60%。提案据此把"命中率 ≥90%(请求)且字节命中率接近 → '优',无优化项或少量提示"定为优档、给低命中域名推荐"加缓存规则",会先把动态业务误判成缓存问题,再给出打偏的优化项。若不区分"全请求命中率"与"可缓存请求命中率"两档,口径是可复现了,但它回答的问题和运维真正想问的问题不是同一个。

风险：请求-字节 gap 的归因只解释了"带宽方向",漏掉了"请求方向"的浪费
> "请求命中率与字节命中率的差距直接对应回源带宽 / 流量费用浪费(大文件未命中 = 高字节回源)" —— 字节命中率低确实指向大文件带宽浪费,但请求命中率低而字节命中率尚可(小文件大量 miss)对应的是回源请求数/QPS 与按请求计费的浪费。提案的归因模型没有把两个方向拆开,优化项里的"未命中流量占比"也只按字节口径计量,请求侧 miss 集中的域名会被漏掉或误归类到"大文件"动作。

**接着看跨源归一与覆盖范围。** 这是我这个岗位翻过车的地方。

风险：提案把 EdgeOne 当作"未映射、需降级"的既定前提,但当前代码已经把 EdgeOne 的 EdgeCacheStatus 映射为 cache_hit
> "EdgeOne cache_hit 未映射(降级标注,不阻塞)" / "EdgeOne 等未建 cache_hit 索引的源显式标注(dimension_notes 风格)" —— 我在 D:\Haven\e-cam-service\internal\shared\cloudx\logquery\tencent\eo.go 里核对:eoFieldMap 已把 cache_hit 映射到 EdgeCacheStatus,eoDimensionExpr 使 cache_hit 可以作为聚合分组维度下推,eoMetricExpr 也含 sum_bytes,明细层 eoLog 直接调用 NormalizeCacheHit 归一。也就是说"EdgeOne 无 cache_hit 索引"这个降级前提与现有实现是矛盾的——除非"未映射"指的是前端 /types 聚合白名单未收录 cache_hit,而那是另一回事,需要核对而不能用"未映射"一笔带过。这个前提直接决定"已覆盖源"集合、覆盖范围标注文案与命中率计算范围,前提错了,降级标注就是给用户错误的安全感。

问题：聚合输出的是各源原始列值(hit_info / cacheStatus / HitInfo / EdgeCacheStatus),"归一映射已有"只覆盖明细层,聚合层"原始组名→枚举"的映射没有单源化
> "已有归一映射(Akamai cacheStatus / hit_info / HitInfo),补跨源口径测试" —— 现有 cache_hit 聚合通过 dimGroupExpr 按原始列分组(见 D:\Haven\e-cam-service\internal\shared\cloudx\logquery\aliyun\filter.go),返回的组名是各源原始值,规则引擎要基于这些原始组名归一成 hit/miss/partial/error 才能算命中率。明细层的 NormalizeCacheHit 与聚合层的"组名→枚举"是两条独立路径,提案只说"补测试",没有把这条映射做成单一来源,也没有落到"同一窗口口径一致"的可执行断言上——这正是历史上"某源口径没归一导致月报命中率虚高"事故的温床。

问题：同一窗口可复现依赖并发查询读到同一份数据快照,提案未定义窗口边界与日志延迟到达的处理
> "当前窗并发聚合 cache_hit×host(域名)、×uri(URI 未命中)、×status(状态码命中率)+ sum_bytes(字节命中率)+ 前窗 1 帧(cache_hit 分布对比)" / "命中率口径与 cache_hit 分布聚合可复现(同一窗口口径一致)" —— 当前窗的各维度聚合各自独立发起、各自扫描窗口,若执行时点不同、或 SLS 日志延迟到达导致同一时点各查询看到的数据截止线不同,四个维度算出的"同一窗口"其实是四份略有差异的快照,分子分母来自不同快照时,"可复现"就不成立。窗口按 [start,end) 对齐之外,必须规定以哪个查询的数据为准,或统一在聚合层做快照对齐。

**再看未命中归因与优化项能不能直接下发。** 我对结构化优化项的要求是:域名 + URI 前缀 + 建议动作 + 未命中流量占比四者闭合,并且有证据支撑动作选择。

风险：URI 归因未做查询串归一,"忽略查询串"这条建议动作没有数据支撑
> "优化项:该前缀加/调缓存规则、忽略查询参数" —— 要可靠地给出"忽略查询串",需要先证明 miss 集中在"同 path、不同 query"的 URI 上,这要求 URI 分组前先剥离/归一查询串。提案的 URI 聚合没有说明是否对 query 做归一:若不归一,同一资源带不同参数会被拆成海量不同 URI,miss 集中度被稀释,"忽略查询串"建议无法被数据支持;若归一,又要处理"某些 query 参数确实改变响应内容"的误伤。这条不写清楚,优化项就停留在文案层,落到云控制台改规则时没有依据。

风险："结构化优化项 ≥3"与健康档位"优 → 无优化项或少量提示"自相矛盾,健康站点会被逼着产出凑数建议
> "结构化优化项 ≥3(域名/URI 前缀 + 建议动作 + 未命中流量占比)" 与 "命中率 ≥90%(请求)且字节命中率接近 → '优',无优化项或少量提示" —— 成功标准把"≥3 条优化项"做成硬指标,但关键场景又明确"优"档可以没有优化项。命中率健康的站点为了满足指标会被规则引擎硬凑三条建议,噪音建议污染分析可信度,也违背了提案自己强调的"判据确定可靠"原则。

风险：状态码命中率的分子分母方向没有定义,而且单维度 /aggregate 给不出"状态×cache_hit"交叉表
> "×status(状态码命中率)" / "建议回源校验/缓存规则排除错误码" —— "状态码命中率(4xx/5xx 占比)"有两种读法:一是"命中的响应里 4xx/5xx 占多少"(缓存命中但返回错误 = 错误被缓存,这才是"排除错误码"建议的依据),二是"所有 4xx/5xx 里从缓存返回的占多少"。两个方向导出完全不同的建议。更现实的问题是:现有 /aggregate 是"单维度 + 单指标"(见 D:\Haven\e-cam-service\internal\logquery\service\federation.go 的 AggregateRequest),要做状态码维度的命中率需要"状态×cache_hit"二维交叉,当前接口做不到;若退而用 cache_hit 过滤再按 status 聚合,cache_hit 是归一字段、大概率不可下推(会触发 skipFilter 全量扫描 + 客户端过滤),成本和正确性都有问题。

**再看成本与阈值。** 我按 SLS 扫描量计费算过太多账,对"≤2 帧"这种表述尤其敏感。

风险："一次分析 ≤ 2 次聚合查询"的成本承诺与 WAF 骨架的实际执行不一致,扫描成本被低估约 3 倍
> "一次分析 ≤ 2 次聚合查询(当前窗 + 前窗),手动触发控制 SLS 扫描成本" / "手动触发后 ≤ 2 次聚合查询返回分析结果" —— 我核对了要复用的 WAF 诊断骨架(D:\Haven\e-cam-service\internal\logquery\service\diagnose.go):一次 diagnose 实际并发发出 6 次聚合查询(当前窗 5 个维度 + 前窗 1 帧),代码注释里 AggregateFrames=2 只是"窗口帧"计数(当前窗 + 前窗),不是查询次数。cache-analyze 的当前窗需要 cache_hit、host、uri、status 各维度加 sum_bytes,按单维度聚合接口算至少 4-5 次查询,加上前窗 1 帧共 6 次上下,每次都是对整窗口全量扫描。提案把"2 帧窗口"写成"2 次聚合查询",把真实扫描量低估了约 3 倍——对实测 1453 万请求/1h 这种窗口,这是可观的 SLS 计费差异,成功标准里的验收口径也会因此失真。

风险：大窗口多域名场景没有扫描量上限或拦截机制,SWR 缓存只对重复请求生效
> "大窗口多域名扫描成本 | M | L | 复用聚合并发通道 + SWR 缓存;手动触发 ≤2 帧" —— SWR 缓存只在"同参重复请求"时命中,首次大窗口(比如 24h × 多域名)依然全量扫描;实测单域 1h 已 286 万请求,24h 多域轻松过亿行。提案没有给窗口时长上限、预估扫描量提示或超限拦截,风险表把这一项标成"L 影响"过于乐观——一旦用户用大窗口 + 全域名扫,单次费用可能超出预期,而"手动触发"并不能防止用户自己点一次贵的。

风险：90% 的"优"档阈值没有校准依据,与工作负载无关
> "命中率 ≥90%(请求)且字节命中率接近 → '优'" —— 90% 对纯静态业务合理,对动态占比高的域名是不可达的,会被长期判"差"并持续产出噪音建议。阈值应该参数化,并基于历史命中率分布(分位数)校准,而不是拍一个看起来合理的整数;否则规则引擎的"优/中/差"三档从一开始就没有区分度。

风险：金额级量化承诺未论证换算模型,落地时口径会被质疑
> "请求命中率与字节命中率的差距直接对应回源带宽 / 流量费用浪费(大文件未命中 = 高字节回源),可量化到金额级" —— 回源费用并不等于 (1-字节命中率)×总流量:未命中字节不一定全量回源(上层 CDN/源站缓存命中、回源内网免流),各云回源还有不同定价与流量包;压缩/转码还会改变字节数。不做换算模型与单价来源说明,直接把 gap 换算成金额,会在上线后被计费数据或云侧报表打脸,反而削弱整份分析的信用。

问题：前窗对比只定义了"相邻等长窗口",没有讨论基期选择,时段混比会被误读成趋势
> "前窗对比:命中率较前窗上升 / 下降,标注趋势(↑↓)" —— 缓存命中率与业务时段强相关(白天动态、夜间静态),相邻窗口环比会把"时段变化"误判成"缓存改善/恶化"。要判断"优化是否生效",更该对比的是同一时段的昨日/上周(同比),提案没有给出基期选择规则,或至少标注对比基期的口径。

问题：前窗部分源失败时,趋势 ↑↓ 的方向口径没有定义
> "前窗无数据 → 只给当前窗绝对量判定;单源聚合失败 → per-source 状态标注" —— 错误场景只定义了"前窗整体无数据"和"单源聚合失败"两个端点;中间状态——某源前窗失败、其余源前窗正常——时,↑↓ 是基于部分源的混合结果。提案没有定义趋势方向是否带 per-source 覆盖标注,会把"部分覆盖趋势"读成"全量趋势"。

问题：域名命中率排行会混合"双口径"与"仅请求口径"的域名,直接排序会误导
> "域名命中率 Top 8、未命中 URI TOP(每域名前几)" / "缺失源降级为仅请求命中率并标注" —— 字节命中率缺失的源降级为"仅请求命中率",但域名 Top 8 若把两种口径的域名按同一列命中率排在一起,读者无法判断"第 2 名比第 3 名好"是真实差距还是口径差异。排行必须按口径分组或加角标,否则又是"部分覆盖被读成全量结论"。

## Improvement Suggestions

把风险按"先锁口径、再定成本、后修归因"的优先级来改,最有杠杆的改动排在最前面。

建议：把成本承诺从"2 次聚合查询"改成"2 帧窗口"口径,并显式列出当前窗各维度查询清单与预估扫描量
Addresses: 风险"≤2 次聚合查询成本承诺与 WAF 骨架实际执行不一致" 与 风险"大窗口多域名无扫描量上限"
> What changes: NFR 与成功标准里的"≤ 2 次聚合查询"改为"当前窗 + 前窗 2 帧窗口,当前窗含 N 次维度聚合"的真实表述(与 diagnose.go 的 AggregateFrames 语义对齐);同时增加窗口时长上限(如最长 24h)、扫描量预估与超限拦截,大窗口给出"预计扫描 X 亿行、约 Y 元"的确认门槛。改完后成本约束可审计,用户知道自己点的这次分析要花多少钱。

建议：重新核对 EdgeOne 的 cache_hit 聚合能力,把"已覆盖源集合"与覆盖标注做成运行时来源而非硬编码
Addresses: 风险"EdgeOne 未映射前提与现有代码矛盾"
> What changes: 实现前先跑一次 EdgeOne cache_hit × sum_bytes 的真实聚合验证(代码已具备 eoDimensionExpr 映射);若可聚合,把 EdgeOne 移入"已覆盖源"并更新降级范围与文案;若聚合白名单确实未收录,明确说明差异点(映射 vs 白名单)并把它列为待办。覆盖范围标注应从聚合返回的 per-source 状态推导,而不是写死"EdgeOne 降级"。

建议：字节口径单独处理 partial,或至少文档化其高估幅度,并为各源 partial 语义补映射单测
Addresses: 风险"partial 全量计入命中导致字节命中率高估"
> What changes: 若源日志能给出 partial 命中字节则按比例折算;不能时,在结果与卡面显式标注"partial 按全命中计,字节命中率存在上偏,方向是低估回源浪费";为 Akamai REFRESH 族、DCDN hit_info、EdgeCacheStatus 的 partial 归类各写单测锁定语义,并在"请求-字节 gap"的解读里说明这一上偏对 gap 方向判断的保守性。

建议：命中率分母分层为"全请求"与"可缓存请求"两档,健康档位与优化项只对可缓存口径生效
Addresses: 问题"请求命中率分母混入不可缓存请求" 与 风险"90% 阈值无校准依据"
> What changes: 规则引擎同时算"全请求命中率"和"可缓存请求命中率"(排除动态/POST/4xx5xx/Range 等不可缓存响应);"优/中/差"档位与优化项生成基于可缓存口径;全请求口径保留展示但不参与判定。这样动态业务不再被误判,优化建议只会指向真正可缓存的 miss。

建议：优化项数量从硬性"≥3"改为"按未命中流量占比降序的 Top N,健康时合法为 0"
Addresses: 风险"优化项 ≥3 与优档无建议矛盾"
