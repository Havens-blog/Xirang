# Freeform Expert Review

> Reviewer persona: 企业证书台账与生命周期风险可见性架构师（10 年多云证书管理平台研发）。评审以「口径闭合」为第一原则，其次核对风险信号保留边界与隐藏可发现性。

## Background Assessment

这份提案要解决的问题是：证书台账默认视图平铺全部证书，其中「已过期且引用清零」的证书（如 `*.jlc-robot.com`，refCount=0、非保护期、可删除）不可操作、无风险信号，属于纯噪音，且随换证持续推进会不断累积。核心方案是：服务端在 `GET /certs` 上新增「排除已过期且 refCount=0」的过滤，默认视图不返回这类行，同时在响应中携带隐藏计数，前端工具栏给出「已隐藏 N 张无引用过期证书 · 点击查看」的可见切换提示；关键的安全边界是过滤条件严格限定为 `expired AND refCount=0`——refCount>0 的过期证书是「线上在用过期证」的漂移风险信号，必须始终可见；并且当用户主动筛选「已过期」（含看板卡跳转 `/certs?daysLeft=expired`）时，隐藏不生效，保证与看板「已过期」卡计数（11=11）的口径一致。

提案对我的职业警觉点是有清醒认知的：它明确拒绝了一刀切隐藏所有过期证书（对比表第一行 "Rejected: 丢风险"），把过滤收敛到引用归零这个判据上，把隐藏计数和分页 total 的闭合交给了服务端过滤而非前端吞行，把隐藏行为做成了非静默的可见切换。这是我见过的这类提案里少数几个把「噪音」和「风险证据」的边界主动划清楚的。方案的隐含假设有三个：refCount 是可信且实时的判定信号（来自最近 done 快照）；daysLeft=expired 的豁免语义可以被明确定义并稳定实现；用户会注意到工具栏提示条。这三条假设正是我下面要逐一施压的地方。

## Key Risks

先说我认为最重要的边界问题：refCount 的「零」不等于「无引用」，「未知」更不等于「零」。

风险：refCount 为 null / 未扫描 / 快照缺失的证书可能被误判为「无引用」而隐藏。
> "过滤条件严格限定 `expired AND refCount=0`；单测锁定「有引用过期可见」" — 提案只锁定了「有引用过期可见」这个正向反向用例，但没有定义 refCount 字段缺失、null、或该证书尚未跑过引用关联扫描时的行为。在证书管理平台里，refCount 通常来自最近一次资产关联快照（提案自己也说 "refCount 来自最近 done 快照"），新导入或指纹级记录（如 Evidence 中的 `*.jlc-robot.com` 是 `fingerprint_only`）的引用关联可能尚未建立。如果 `refCount IS NULL` 被当作 0 处理，这些过期证书会在默认视图静默消失——而这恰恰可能是一张刚过期、引用扫描还没跑完、线上仍在用的证书。这是本类「默认隐藏」方案最经典的误藏事故路径：被隐藏的行用户看不见，也不会主动点「查看」，漂移信号就此丢失直到告警爆发。后果是提案要保护的「风险可见性」被自己的过滤条件破坏。

风险：组合过滤下隐藏计数 N 的口径未定义，可能产生新的「11=11」式口径漂移。
> "隐藏逻辑与其它过滤正交（先按其余条件过滤，再隐藏无引用过期行）" — 这句话定义了行的过滤顺序，但没有定义隐藏计数是否同样按其余条件重算。用户在搜索某个域名或筛选某托管状态时，工具栏应该显示「当前筛选结果中有多少张被隐藏」，还是全局的 N？如果 N 恒为全局值（当前 1），而用户搜索的关键词命中结果里根本没有被隐藏的行，提示「已隐藏 1 张」就是错的——用户点「查看」后行数不变，提示与行为对不上，这正是我曾经处理过的「过滤后 total 与行数漂移」引发用户信任事故的同构问题。三方闭合（total、行数、隐藏计数）必须限定在同一过滤上下文内才成立。

风险：daysLeft=expired 的豁免语义收敛在哪一层没有定死，URL 直达和状态切换存在绕过路径。
> "新增「排除无引用过期」参数需与 daysLeft/expired 联动的语义（daysLeft=expired 时不排除）" — 这句话把联动列为一个待定语义，但没有说明：豁免是后端在 daysLeft=expired 时强制忽略 exclude 参数，还是前端在主动筛选时不传该参数。如果豁免落在前端，那么任何 URL 直达路径（看板跳转、浏览器书签、第三方链接带 query 参数）都必须正确地带对参数组合，一个遗漏就是一次 7cdd488 式的口径回归——提案联调断言 "联调断言 11=11" 恰恰说明这类回归真实发生过。后端强制豁免则天然闭合，但也带来「参数存在却不生效」的 API 语义复杂度。这一层不定死，实现者很可能选最省事的前端豁免，把风险留给每一个入口。

问题：用户切换状态与筛选状态机、分页行为未定义，「查看全部」后的恢复语义存在自洽缺口。
> "点击显示全部、再点恢复隐藏，计数与行实时一致" — 提案定义了「查看↔隐藏」的往返，但没定义交叉场景：用户先点「查看全部」（隐藏豁免生效），再选「剩余天数=已过期」，再清除筛选回到默认视图——此时切回隐藏态还是保持显示态？此外切换会改变 total 和行数，若用户停在非第一页（例如第 2 页），切换后该页可能超出新的 total 范围，是重置到第 1 页还是显示空页？Key Scenarios 里 "点击「查看」：无引用过期证书显示出来，提示变「再次点击隐藏无引用过期证书」" 只覆盖了最短路径。状态机缺口在实践中必然表现为联调时才发现的边界 bug。

问题：「无新增查询」的性能声明与「响应返回隐藏计数」存在实现矛盾。
> "性能：无新增查询（复用 listCertsApi，新增一个布尔过滤参数）。" — 服务端过滤后，响应要同时携带两个口径：过滤后 total（分页用）和隐藏计数（提示用）。实现上这通常意味着对同一 WHERE 条件做一次不排除的 COUNT，或一次查询里算两个 total——无论哪种都是一个新增的统计口径/查询动作，与「无新增查询」的字面声明冲突。这不是致命问题，但提案把性能声明写进了 Non-Functional Requirements，实现者照着「无新增查询」做，最可能的偷懒是让前端用某种方式推算隐藏计数——那就又回到了前端口径漂移，恰好是提案风险表 #1 要杜绝的东西。

风险：空态是残余的静默吞行路径，提示条与空态组件的关系未定义。
> "空结果：默认隐藏后无可操作证书 → 空态文案指引（调整筛选/查看隐藏）。" — 提案想到了空态指引，但没有明确「已隐藏 N 张」提示条在空态下是否仍然可见。典型表格实现中，空态组件会替代表格主体，工具栏提示是否随之消失取决于组件结构。设想未来某天所有过期证书都完成换证且引用清零：默认视图过滤后为空，用户看到一张空表和空态文案——如果此时提示条不在空态视图中，「有证书被隐藏」这个事实只剩一行小字，静默吞行以最彻底的形式复现。今天 N=1 不会触发，但这个方案的寿命是以年计的。

问题：「不可操作噪音」的判定与提案自己的证据存在逻辑张力——这张被隐藏的证书恰恰是唯一可操作的。
> "其中 **1 张 refCount=0**（`*.jlc-robot.com`，-11 天，fingerprint_only，非保护期，可删除）" — Problem 一节把无引用过期证书定义为 "不可操作、无风险信号"，但 Evidence 自己承认它是 "可删除" 的：refCount=0 且非保护期，意味着这是台账里少数可以执行清理动作的行。隐藏它等于把「可清理的对象」藏了起来——用户失去了发现「这里有一张过期证可以顺手删掉」的机会，噪音治理的目标（可操作性）与手段（隐藏）在这一点上是相反的。隐藏让列表干净了，但也让清理路径的入口变深了。fingerprint_only 这个属性还叠加了第一风险：指纹级记录的引用判定置信度本身就低于完整证书。

问题：验收标准把当前快照的数字硬编码成了断言。
> "11 行 = 看板「已过期」卡计数 11" — 提案自己在 Evidence 里说 "换证操作正在持续进行"，过期数量是随时间变化的活数据。把字面 11 写进 Success Criteria，意味着今天验收通过、两周后换证完成数量变成 8 时，这条验收标准就变成了一条永远无法满足的假断言，或者反过来误导实现者写死数据。口径一致断言的价值在于「行数=卡计数」这个相等关系，不在于具体是几。

## Improvement Suggestions

按对上述风险的覆盖优先级排列：

建议：给 refCount 判定加保守兜底——只有「扫描已完成且显式为 0」才判为无引用，null/未知一律视为有引用（显示），并把这两个用例写进后端单测。
Addresses: refCount null 误藏风险、fingerprint_only 置信度问题
> What changes: 在 Risks 表 #2 的 Mitigation 中把 "过滤条件严格限定 `expired AND refCount=0`" 扩展为 "过滤条件严格限定 `expired AND refCount IS NOT NULL AND refCount=0`（refCount 未知/未扫描的过期证书保守显示）"；在 Success Criteria 增加单测要求：refCount=null 的过期证书默认视图可见、fingerprint_only 且 refCount=0 的证书行为有明确定义的用例。这把「有引用过期可见」的反向用例补成了完整的边界矩阵，是防止本方案变成事故的最关键一行代码级约束。

建议：明确隐藏计数按当前其余过滤条件重算，由服务端在同一响应中返回两个口径（visibleTotal 与 hiddenCount），禁止前端推算。
Addresses: 组合过滤下隐藏计数口径漂移问题、「无新增查询」矛盾
> What changes: 在 In Scope 第一条 "响应返回隐藏计数" 后追加口径定义："隐藏计数 = 满足当前 search/hostingStatus/daysLeft 之外其余过滤条件但被隐藏的行数（与 visibleTotal 同一过滤上下文）"；同时把 Non-Functional 的性能声明改写为 "复用 listCertsApi 主查询，仅新增一次同条件统计口径（或单查询双 total），不新增独立接口"。提案需要的是诚实的性能描述加收敛的口径定义，二者都在 Key Scenarios "结合托管状态/搜索过滤：隐藏逻辑与其它过滤正交" 这一条中一并写死。

建议：把 daysLeft=expired 豁免收敛到后端——服务端收到 excludeUnrefExpired=true 且 daysLeft=expired 时强制忽略排除，前端无需感知豁免；并在提案中写明切换状态与筛选状态机的优先级。
Addresses: 豁免联动收敛层未定死风险、切换状态机缺口
> What changes: 在 Constraints & Dependencies 中把 "需与 daysLeft/expired 联动的语义（daysLeft=expired 时不排除）" 落成明确决策："豁免由后端强制执行，exclude 参数不改变 daysLeft=expired 语义；前端豁免逻辑不存在"。同时补一段状态机定义：用户切换态（查看全部/恢复隐藏）仅作用于默认视图；进入 daysLeft=expired 筛选时切换态挂起（显示全部）；清除筛选后回到切换态定义的视图；切换导致 total 变化时分页重置到第 1 页。看板跳转 "7cdd488）必须保持显示全部过期" 就从「前端记得做对」变成「后端天然保证」，联调断言 11=11 的脆弱性随之消除。

建议：明确空态下「已隐藏 N 张」提示条必须保留，作为可发现性验收项。
Addresses: 空态残余静默吞行路径
> What changes: 在 Key Scenarios 空结果一条后追加："空态视图中仍显示「已隐藏 N 张…」提示与「查看全部」入口（提示条不随表格主体消失）"；Success Criteria 第二条同步加上空态场景。这堵住了本方案寿命内最可能出现的一次「看起来没有证书」的误读。

建议：把验收断言从硬编码 11 改为动态相等关系，并在文案上对「可删除」属性给出顺手清理的引导路径（但不扩 Out of Scope）。
Addresses: 硬编码快照数字问题、可删除对象被隐藏的逻辑张力
> What changes: Success Criteria 第四条改为 "daysLeft=expired 筛选结果行数 = 看板「已过期」卡计数（动态相等断言，不写死数值）"；同时行内提示文案可考虑为「已隐藏 N 张无引用过期证书（可删除）· 查看全部」，让被隐藏行的「可操作」属性对用户可见——这是在不触碰 Out of Scope（不引入批量删除）的前提下，把提案自己认定的清理机会留在用户视野内的最小改动。若认为文案改动超范围，至少应在 Key Scenarios 中承认并记录这个取舍：被隐藏的行包含可删除对象，查看入口是其唯一发现路径。
