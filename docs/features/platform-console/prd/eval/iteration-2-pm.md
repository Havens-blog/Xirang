**本轮新发现（pre-score anchors）**：

A. **锁定提示与防枚举规则互相牵制（修订新引入的张力）**：UF-1 Validation Rules `认证失败不泄露用户名是否存在`，而 UF-1 States 与 E2/E9 承诺 `锁定提示+剩余解锁时间`——「账号已锁定、还剩 N 分钟」只有在该用户名真实存在且被锁定时才成立，等于向探测者确认账号存在。两条规则各自合理，同页并存即冲突，须界定非泄露规则的适用范围（仅凭据错误提示）或改用中性文案（如「尝试过于频繁，请稍后再试」）。

B. **passkey-only 账号的注册引导路径不可实现**：UF-4 新增 `登录方式 | 密码/passkey（passkey 经注册引导绑定，WebAuthn 可用时）`，校验 `passkey 账号完成注册引导才可提交`。WebAuthn 注册仪式需要用户本人的认证器在场——管理员代建 passkey-only 账号时仪式由谁、在哪个浏览器完成，PRD 未定义；设备丢失后重绑路径同样缺失（E1 只覆盖密码重置）。修订新增的字段引出了一个未闭合的流程。

C. **E1 措辞移植错误（轻）**：`管理员重置 → …该用户首次登录强制改密`——被重置的是存量用户，其下一次登录并非「首次登录」。语义可推断但措辞不精确。

D. **迁移门只测端点 parity，不测被迁页面功能 parity**（详见 Blindspot 1）：`parity-checklist.md` 的盘点对象是端点差集，而迁移动作的承诺是「消除双处维护」——若 e-cam-web `platform/users` 页面存在 UF-4 未覆盖的能力，迁移即静默降级且门禁放行。

E. **正向确认（不得因扣分而无视）**：UF-6 禁用前置已给出可测定义（`未过期会话数 = 0（活跃用户 = 存在未过期共享 session 的用户）`并给出被拒 UX）；E6 并发编辑给出 409 分支与 Phase 0 核查归属；E11 依赖删除被拒给出了弹窗 + 置灰的具体 UI 态；Quality Checklist 已改为证据链接式。文档当前的证据纪律是真实的。

## Phase 3 — Blindspot Hunt

**[blindspot] 1 — 迁移门禁度量对象错位：端点 parity ≠ 被迁页面功能 parity。**
In Scope 承诺 `从 e-cam-web 迁出平台身份 UI（platform/users），消除双处维护`，Related Change 1 的前置门是 `parity-checklist.md 逐项覆盖且逐项附 evidence`——但 Phase 0 的盘点对象是 `端点差集盘点 + 认证链路事实核查 + 服务端授权核查`，全部是 eiam 侧端点，没有一行要求盘点 e-cam-web `platform/users` 现有 UI 能力清单并与 UF-4 逐项对齐。推导：若旧页面存在 UF-4 未规格化的能力（如批量操作、密码策略设置、导入导出），端点 parity 可以 100% 通过，而迁移在用户可见层面静默丢功能——门禁放行、承诺落空。本文档在其他所有门禁上都建立了 evidence 纪律（双签、截图、接口响应），唯独迁移这一最大的用户可见变更缺了输入清单。Reasoning audit anchor D 独立发现了此问题。必须改进：在 Related Change 1 前置门中增加「platform/users 现有能力清单 + 与 UF-4 逐项映射，缺口按三类处置（并入 UF-4 / 登记降级 / 业务确认放弃）」。

**[blindspot] 2 — eiam API 契约稳定性未做任何约束。**
方案的前提是 `直调 eiam 已有 API`（What 段）与 `复用 eiam 现有端点，不自建`（DF001/DF003 Notes）。Phase 0 在某个时点盘点端点、会签认证矩阵，但 5.5–6.5 人周的开发期内 eiam 端点若发生变更（改名、改语义、下线），前端无任何防护，也没有变更通知/契约冻结的机制性条款。认证链路有 `认证链路兼容矩阵…经 eiam 后端 owner 书面会签`，CRUD 端点只有盘点没有冻结。对一个零后端、全部依赖外部 API 的产品，这是最大的单点交付风险，却不属于任何 rubric 维度（D7 只管范围清晰，D1 只管目标）。必须改进：声明「eiam CRUD 端点契约基线 = parity-checklist 快照 + 开发期内端点变更须书面通知并评估影响」或等价的变更控制条款。
