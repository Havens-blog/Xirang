## Phase 1 — Reasoning Audit（独立推理审计）

**Problem → Solution 链条**：问题（ecmdb-web 下线 → 平台身份/权限/工作台 UI 断供 + 依赖他人前端违背「100% 可控」）→ 方案（纯前端控制台直调 eiam、共享 Redis session、Phase 0 决策门兜底端点差集）。链条成立且自洽：`直调 eiam 已有 API` 与 `除 eiam 外零新增后端` 互证；parity 公式（`覆盖率 = 已覆盖项 ÷（总项数 − 「放弃」项）`）使 Goal 1 与 Related Change 3 的三类处置双向可满足。方案成立的前提（eiam 端点足以支撑 parity）未被断言为事实，而是由 Phase 0 清单 + 契约基线 + 三类处置门显式接管——风险显性化是真实的。

**上轮 13 条合并攻击点复核（详见附录）**：13/13 在当前页面均有对应修复，其中 9 条完全闭合，4 条闭合但各自留下一个次生残留（见下）。

**本轮新发现（pre-score anchors）**：

A. **LDAP 用户在用户模型中无落点（本轮最重发现）**：UF-1 支持三种登录方式（`system/ldap/passkey`），UF-7 管理身份源（含 `用户属性映射：用户名/邮箱/DN 属性名`），但 UF-4 的用户模型是 `登录方式 | enum | eiam | 密码/passkey（passkey 经注册引导绑定，WebAuthn 可用时）`——没有 LDAP 选项。推导：经 LDAP 认证的用户要么不存在于 /users 目录（则平台管理员看不到、管不了他），要么必须以「密码/passkey」之外的形态存在（则 UF-4 的字段模型漏了它）。身份源与用户目录的关系语义（同步/JIT 建档/仅认证不建档）在三份文档中零定义。E10 的用户名字符集 `^[a-z][a-z0-9_-]{2,31}$` 不含点号与大小写，与典型 LDAP 账号命名（如 john.doe）冲突，规则适用范围（是否仅限 UF-4 表单新建）亦未声明。

B. **图中零租户分支与 E3 平台管理员豁免矛盾（修订部分引入）**：E3/Flow #3/UF-11 三处文本均已补平台管理员豁免（`零所属租户仍可访问全部管理页`），但流程图未同步——`TenantCount -->|0 个| WorkbenchZero[直达工作台受限视图, 仅欢迎+我的信息]` 与 `WorkbenchZero -->|访问管理页| NoTenant[提示「无所属租户」, 不报错不白屏]` 对零租户平台管理员无条件成立。按图走：零租户管理员被压进受限视图并被「无所属租户」提示拦在管理页之外，与 E3 豁免直接冲突。豁免是按角色条件分流，图中无该判定节点。

C. **登出确认语义图文不符（轻）**：图中 `Logout{确认登出}` 是决策节点但只有一条出边（`|单点登出|`），无「取消」分支；UF-2 交互流程 `点登出 → 双侧会话失效` 与 Flow #7 均无确认步骤。确认与否两处表述不一致，且决策节点形态不完整。

D. **禁用用户的会话吊销语义缺失（与租户禁用不对称）**：UF-6 租户禁用有可测前置（`该租户下未过期会话数 = 0`），UF-4 用户禁用（`状态 | enum | eiam | 启用/禁用/锁定`）无任何会话/生效语义——被禁用用户的活跃共享 session 是立即失效、下次请求被拒还是存活至自然过期，三份文档零定义。对身份治理产品，禁用是安全动作，吊销时延是其核心验收属性（对比：S4 对「删除授权」已给出 `生效延迟 ≤ 30 秒`，对「禁用用户」反而没有）。

E. **回切开关的受控对象未定义**：`上线前回切开关演练（10 分钟内可回切）`——回切什么？Related Change #2（401 跳转目标）是 e-cam-web 请求层的代码改动，若非运行时可配置，「10 分钟回切」缺乏机制载体（开关控制 401 目标？登录入口路由？DNS？）。回滚语义对一个零后端前端 + 硬编码跳转目标的架构不是自明的。

F. **正向确认（不得因扣分而无视）**：验收约束四要素齐备（映射矩阵/负向占比/产出阶段与 owner/完成形态）；能力映射使迁移门从端点 parity 扩展到功能 parity（`未经映射的能力项不得标记「已覆盖」`是硬约束）；契约基线条款带 `≥ 5 个工作日书面通知` 与未通知变更的回归触发；M1–M4 均有范围与出口判据且与 UF 编号互锁；UF-1 防枚举边界已收窄到凭据错误提示并给出中性锁定文案。文档当前的证据纪律与口径管理是真实的。

## Phase 3 — Blindspot Hunt

**[blindspot] 1 — 跨仓库变更（Related Change #1/#2）在验收签署链中无 owner 会签。**
验收约束规定 `前端 owner + 测试 owner 双署，涉 eiam 断言须 eiam owner 会签`——eiam 侧断言有具名会签人，但 Related Changes 表中 #1（`e-cam-web | views/platform | 移出 platform/users`）与 #2（`e-cam-web | 请求层 | 会话过期/401 跳转目标`）都是 e-cam-web 代码库的改动，而「前端 owner」未声明指控制台前端还是 e-cam-web 前端；401 跳转目标切换的验收（S6 AC 只覆盖登出方向）实际执行方与签署方处于口径真空。这是交付治理缺口，不属于任何 rubric 维度（D7 只管范围清晰，D4 只管 story 可验性）。Reasoning audit 未单列此条，属本轮独立发现。必须改进：验收约束中显式声明「涉 e-cam-web 改动的场景须 e-cam-web 前端 owner 会签」或等价的跨仓库签署条款。

**[blindspot] 2 — 契约基线的「关键」子集未划定，端点级变更通知可能被泛化执行。**
`Phase 0 冻结本控制台依赖的 eiam 端点快照（路径/方法/鉴权要求/关键字段）登记入 parity-checklist.md 作为契约基线；eiam 侧变更基线内任一端点…须提前 ≥ 5 个工作日书面通知`——条款本身完备，但其执行面是「本控制台依赖的」端点集合，而依赖集合由 Phase 0 产出、无任何机制防止 eiam 侧把通知义务泛化到全量端点（通知疲劳）或收窄到漏掉隐式依赖（如 UF-6 禁用前置隐含的「按租户统计未过期会话数」端点、E2/E9 隐含的「剩余解锁时间」查询端点——这两个端点是否入基线取决于盘点颗粒度，而盘点颗粒度未定义）。一份依赖外部 API 的零后端产品，其契约保护的实际效力取决于「依赖集合」枚举的完备性判据，该判据缺失。必须改进：声明基线枚举判据（如「UF 数据表 Source 列出现的每个 eiam 依赖 + 每个隐含查询端点逐条登记」）。
